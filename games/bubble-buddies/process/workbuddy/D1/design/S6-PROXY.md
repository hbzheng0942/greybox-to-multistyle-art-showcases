## 一句话结论

灰盒的构图跟 H1 纸面推演**有一处方向性错误**：宠物在 1280×800 里实际是 **71–73 px 高**，不是推演时的 24–32 px——因为 52.8° 俯角把身体**纵深**也算进了屏幕高度。同时员工只有 76–79 px，比宠物高 4–8%，**靠大小分不开人和宠**。这两条直接改写 D1 的像素预算和辨识方案。

## 七条基線风险：全部观测到，全部有处置

| 风险 | 处置要点 |
|---|---|
| 隔墙 / 窗 / 墙垛可读性 | 不给墙垛形体。台面做成一条连续石材带，用顶面纹样 + 两团独立暖光表达"两个洞"；窗框压平、不做高光，别在宠物前面立一根竖棂 |
| 员工 vs 宠物轮廓混淆 | 尺寸已证伪。改用两个非尺寸信号，都放在轮廓顶部：员工=饱和单色外套 + 一个硬配饰（帽/围裙角），宠物=耳/毛簇，永不共用外套色 |
| 地面与顶面主导 | 顺从而不是对抗：地面是最大美术面（两种分区材质 + 灰缝/纹理方向），台面靠贴花、工具、接触道具，只有后墙和窗前那段立面值得做细节 |
| 干湿分区不能只靠颜色 | 加三条非颜色信号：x=0 处地面纹样与方向突变、2.45–4.75 门洞的门槛条、两室不同的物件族（地漏/龙头/软管 vs 货架/刷具/叠布） |
| 17 工位辨识 | 每个工位加一个**破轮廓**的台面以上道具，≥0.4 m 高；关掉标签后 17 个仍能靠形状成套区分 |
| HUD 压在繁忙画面上 | **实测不成立**：房间 y 120–637，637–652 是纯背景，底栏从 653 起，六张图里没有任何 HUD 面板压到房间。真正的问题是世界标签 |
| 24–58 px 小尺寸可读性 | 按 ~72 px 预算：一次五官读取 + 一次状态读取（炸毛球/歪刘海），约 3 px 以下不做纹理 |

## 五个未决制作项（不阻塞 H3，但必须有人认领）

1. **窗口比宠物小**：窗洞 0.72–1.96 m 投影约 40 px 高，宠物 72 px，溢出约 1.8 倍。永远塞不进"整齐的窗洞"，只能做成"趴在台面上探出来"。
2. **57% 画面是空的**：目前没有任何归属。这是"店在街上"这类主意唯一能落脚又不碰玩法的位置。
3. **交付奖励在画面边缘**：宠物走人、主人等待都在 134 px 宽的接宠院里，还隔着 0.7 m 矮墙；宠物的状态标签正好压在宠物与主人之间。
4. **31 个世界标签是辨识拐杖**：字号只有几个像素高，一被遮挡就没了。它属于工位辨识任务，不属于 HUD。
5. **基线声明与代码不符（已修正记录）**：`spatial-contract-v1.json` 把 v-frizz-recovery 写在 wet_room，但代码里炸毛只可能在烘干台（dry room）产生、只可能在美容台（dry room）补救。冻结的基线**没有改**，修正记在 `composition-probe.json` 的 `declaration_correction` 里，探针拍的是真实位置。
